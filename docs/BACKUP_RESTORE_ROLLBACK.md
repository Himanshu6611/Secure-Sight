# Production backup, restore, and rollback

The SQLite database and its encryption key form one recovery set. Store the database backup in encrypted, access-controlled storage and escrow `DASHBOARD_ENCRYPTION_KEY` separately under the organization's recovery procedure. A database copy without the key is unusable; a key without the database does not restore records. Include SQLite WAL state by using SQLite's online backup API or by quiescing the service and copying the database plus any `-wal`/`-shm` files. Never copy a live database file alone and assume it is consistent.

Before an image upgrade, record the current image digest and take a verified database backup. Start the new digest with the same persistent volume and keys, then check `/api/v1/ready`, the dashboard login, and `flask --app app:create_app dashboard-audit-check` inside the container. Keep the old image digest available for rollback. If the new release fails, stop it and restore the old image digest against the same volume only after confirming that the database schema remains compatible. Current schema changes are additive `CREATE TABLE/INDEX IF NOT EXISTS` operations at application startup; no down-migration is provided. For any future destructive schema change, restore a backup to a separate copy and follow a release-specific migration plan rather than assuming image rollback reverses database changes.

Do not validate recovery by overwriting the live volume. Perform a restore rehearsal against a separate temporary volume, verify audit-chain integrity and expected records, then securely remove the rehearsal copy according to retention policy. The repository does not automate encrypted backup, off-site replication, retention, or restore testing; assign an operator and schedule these before accepting production data.
